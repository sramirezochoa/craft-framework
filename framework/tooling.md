# Tooling

The only file in `framework/` allowed to mention specific tools. Everything
else stays tool-neutral so that any agent, or no agent, can follow the process.

Expect this file to go stale faster than the rest. Check against current
vendor docs when something does not match.

---

## 1. Cross-platform strategy

Collaborators run Windows, macOS and Linux. The rules that keep that working:

| Rule | Why |
|---|---|
| Entry point is the project's build tool (`./mvnw`, `./gradlew`, `npm`, …) | Works identically on all three OSes without extra installs |
| Shell scripts are POSIX-simple bash | Portable between Git Bash, WSL, macOS and Linux |
| Anything non-trivial is Python, not bash | One behaviour everywhere; no GNU-vs-BSD `sed` surprises |
| `make` is **not** assumed | Not present on Windows by default |
| Scripts invoked as `bash scripts/x.sh` | Windows does not track the executable bit |
| `.gitattributes` forces LF on `*.sh` | CRLF in a shell script fails with baffling errors |
| Adapters are **copied**, never symlinked | Symlinks need Developer Mode on Windows and break silently |
| CI runs on `ubuntu-latest`, `macos-latest`, `windows-latest` | The only real proof |

### Supported Windows environments

In order of preference:

1. **Dev Container** (Docker + `devcontainer.json`) — identical environment for
   everyone. Best option if collaborators can run Docker.
2. **WSL2** — a real Linux. Keep the repository *inside* the WSL filesystem,
   not under `/mnt/c/`, or file watching and performance suffer.
3. **Git Bash** — ships with Git for Windows, so nearly everyone already has it.
   Works, with caveats: no `make`, path translation quirks, a thinner toolset.

Record which one your collaborators use in `docs/overview.md`.

### Prerequisites

`bash scripts/verify.sh` checks all of these in its preflight stage and tells
you what is missing, so the quickest check is to run it.

| Tool | Required? | What needs it | Check |
|---|---|---|---|
| **Python ≥ 3.8** | **Hard** — nothing runs without it | `framework/craft.py`, which is the whole toolchain | `python3 --version` |
| **bash** | **Hard** | `scripts/verify.sh` and your `verify-impl.sh`. Ships with Git on Windows | `bash --version` |
| Your language toolchain | **Hard** | Building and testing. Wired up in `scripts/project/verify-impl.sh` | per project |
| Git ≥ 2.30 | Recommended | Branch conventions, and `craft.py upgrade` checks for a dirty tree | `git --version` |
| shellcheck | Optional | Keeps the two shell files portable. CI runs it regardless | `shellcheck --version` |

Standard library Python only — there is nothing to `pip install`. Python 3.8
is the floor because every type annotation sits under
`from __future__ import annotations`.

No Node, no Make, no Docker, and no framework-specific package.

## 2. Agent adapters

The canonical files are tool-neutral. `framework/craft.py sync` copies them
into whatever locations each tool expects. CI fails if the copies are stale.

| Canonical | Purpose |
|---|---|
| `AGENTS.md` | Instructions. Read by Codex and a growing number of agents |
| `framework/skills/<name>/SKILL.md` | Reusable procedures |
| `mcp/servers.yaml` | Connector list, from which tool configs are generated |

| Tool | Adapter | Generated by |
|---|---|---|
| Claude Code | `CLAUDE.md` → `@AGENTS.md` | committed |
| Claude Code | `.claude/skills/` | `craft.py sync` |
| Claude Code | `.mcp.json` | not generated yet — write it by hand |
| Codex | reads `AGENTS.md` natively | — |
| Codex | skills / MCP config | not generated yet |
| Cursor | `.cursor/rules/` | `craft.py sync` |

Generated adapters are committed. `bash scripts/verify.sh` fails if they are
out of date; regenerate with `python3 framework/craft.py sync`.

> **Verify the exact paths against current docs for each tool before relying on
> them.** Agent tooling moves fast, and `craft.py sync` is deliberately the
> single place to absorb that churn. Adding or correcting a target is an entry
> in its `SYNC_TREES`, `SYNC_FILES` or `SYNC_WRITES` table.

### Skills

A skill is a folder containing `SKILL.md` with YAML frontmatter (`name`,
`description`) and markdown instructions. The format is shared across several
agents, which is why the canonical copy lives in `framework/skills/`.

If your agent does not support skills, open the `SKILL.md` and follow it. They
are written to be readable by a person.

### What stays tool-specific

Hooks, subagents and slash commands are **accelerators, never the only place a
rule lives**. Anything enforced by a Claude hook must also be enforced by
`verify.sh` and CI, or Codex users silently lose the guardrail.

Keep such extras under `adapters/<tool>/`, clearly marked optional.

## 3. The verify entry point

`scripts/verify.sh` is the executable definition of "passing". It runs:

1. Lint / static analysis
2. Unit and integration tests
3. Eval suite (if `evals/` has cases)
4. Traceability and drift check (`framework/craft.py drift`)

Wire it to your build tool by defining `project_lint` and `project_test` in
`scripts/project/verify-impl.sh`. Keep that file thin — real logic belongs in
the build tool or in Python.

The same script runs locally, in the git pre-push hook (optional) and in CI.
One definition, three places.

---

## 4. Connectors (MCP)

`mcp/servers.yaml` is the canonical list. Each entry records what it is for and
whether it is required. Generating each tool's config from it is planned but
not implemented yet: `craft.py sync` only notes that the file exists, so keep
`.mcp.json` and other tool configs in step by hand for now.

Credentials never go in the file. Reference environment variables only.

## 5. Conformance test

The portability claim is only true if it is tested. Periodically:

1. Take a small reference change.
2. Run the full lifecycle with Claude Code, then with Codex, from a clean state.
3. Both should produce: a change spec, a plan, failing tests, passing `verify`,
   and an updated capability doc.

Where the two diverge, the instructions were too tool-specific or too vague.
Fix the instructions, not the tool.
